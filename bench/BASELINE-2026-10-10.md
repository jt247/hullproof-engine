# Phase 0 baseline, 2026-10-10

This is the first machine scored baseline for Hullproof. It rescored the audit outputs we already had, using the scorer in `bench/score.ts`. No new model audit was run and nothing was downloaded. One extra row, the deterministic scan, came from running the Semgrep and Gitleaks binaries already installed on this machine, with the kit's own rules, against the demo app source. No model was involved in that row.

## How to reproduce

```
./bench/run-baseline.sh
```

The script checks the inputs (the raw audit outputs, which are not published) against a list of SHA-256 sums, scores them against the demo key (the private copy of the demo answer key, which lists requirement IDs for every flaw (the `DEMO-ANSWER-KEY.md` published in the hullproof-demo repository shows none for the Pro flaws)) with the class file `bench/keys/demo-classes.json`, and writes `bench/results/baseline-2026-10-10.json` and `.md`. I ran it twice and the JSON had the same SHA-1 both times (6bd1fe30). The matching method is in `docs/SCORING.md`.

All the audited copies hold the same application. The git tree hashes of `src`, `supabase`, `.github`, `next.config.js` and `package.json` are identical in all six copies (for example `src` is 5e0116f7 everywhere). The commits differ only because each copy carried a different kit install.

### Precision

The key does not list every true finding, so a true precision cannot be computed. The scorer reports a flagged precision: findings that match a planted flaw, against findings that match only something the key says is done correctly on purpose. It is an upper bound.

|---|---|---|---|---|
| codex-pro-0.3.0 | 48 | 2 | 55 | 0.96 |
| codex-free-0.3.0 | 25 | 1 | 52 | 0.962 |
| codex-pro-0.3.1 | 25 | 0 | 38 | 1.0 |

Every flagged item was already called doubtful by a hand score or is the same kind of claim: the CSP sandbox note on file downloads (NP4, Codex Pro), the in memory AI budget (NP3, Codex Free and Claude run 3), and scrypt at default cost (NP2, Claude run 4; run 1's hand score called the same claim doubtful). The unmatched units are mostly extra true findings and records gaps; the earlier hand scores checked many of them and found no clear false claim about the code. Four unmatched units of the deterministic scan are rule hits outside the key, including `hullproof-server-action-no-auth` on `profile.ts:15`, which the earlier scorecard already called a false positive.

### Stability

There is no true stability number yet. Stability means the same kit, the same model and the same commit run three times, and we have no such set. What we do have is agreement between related runs:

| Pair | Same status | Verdict |
|---|---|---|
| Codex Pro 0.3.0 against Codex Pro 0.3.1 (kit changed between them) | 24 of 30 (0.8). Differ on P01, P04, P10, P13, P14, P15 | NOT READY both |
| Claude run 3 findings against Claude run 4 findings (kit fixes between them) | 23 of 30 (0.767). Differ on F07, F14, P02, P04, P06, P10, P14 | not readable from records |

Across all eight model outputs no flaw has the same status in every output. That mixes kits, models and output types, so it is not a stability figure either, but it is the honest picture of what a user saw from run to run.

## Comparison with the hand scores

The hand scores were written by the maintainers and are not published.

| Output | Hand score (found, partial, missed) | Scorer | Same? |
|---|---|---|---|
| Codex Pro 0.3.0 | 24, 1, 5 | 24, 1, 5 | Same on every flaw |
| Codex Free 0.3.0, Free scope | 15, 0, 0 | 15, 0, 0 | Same |
| Codex Free 0.3.0, Pro only bonus | P07, P12, P13 found; P08 and P09 mentioned in passing | P07, P12, P08, P09 found; P13 partial | Differs on P08, P09, P13 |
| Claude run 1 reply | 15, 1, 14 | 14, 2, 14 | Differs on F11, F12, P09 |
| Claude run 3 report | 21, 5, 4 | 21, 2, 7 | Same totals for found; differs on 6 flaws |
| Codex Pro 0.3.1, Claude run 3 findings record, Claude run 4 findings record | not hand scored | see above | not applicable |

Why they differ. Each difference comes from one of four rules, and each rule is deliberate.

1. The scorer needs a file the key names, in the same finding. The hand scorer accepted prose. Claude run 1 says "the session token is logged at login" and "the API reflects any origin with credentials" with no file, so F11 and F12 drop from FOUND to PARTIAL. Codex Free F-22 places the audit gap in "Admin, authorization, and authentication handlers" with no file, so P13 is PARTIAL. Claude run 3 F-23 cites `middleware.ts` for the missing login rate limit; that file belongs to other flaws in the key, so P01 drops from FOUND to MISSED.
2. A finding at a file the key does not name, with the right defect, is PARTIAL. Claude run 3 F-28 cites the redirect sink `login/page.tsx:23` and not `login/route.ts:25`, so P12 drops from FOUND to PARTIAL.
3. A requirement ID on the right file counts as the defect class. The hand scorer wanted the defect described as its own finding. Codex Free F-16 and Claude run 3 F-14 list a Pro requirement ID or name the write all token on `ci.yml`, inside the CI injection finding. The scorer counts P08 and P09 as FOUND there; the hand scorer said PARTIAL or "in passing". The same rule turns Claude run 1's P09 from PARTIAL to FOUND.
4. The scorer has no "right area, vague defect" rule, because that needs judgement. Claude run 3 F-36 ("unbounded schema strings") and its HSTS finding were PARTIAL by hand for P10 and P04. The scorer finds neither the key's IDs nor the key's defect words (caps, timeout, CSP, frame, nosniff, referrer), so both are MISSED.

The other way round, one rule makes the scorer kinder than a careful reader: it does not check that every part of a compound flaw is covered. Claude run 3's findings record covers upload size but not upload type for P11, and the scorer counts FOUND because the file and the word "upload" are there. The hand score of the agent union had called this PARTIAL.

My read: the scorer agrees with the hand score exactly on the cleanest output (Codex Pro 0.3.0) and on the Free scope, and the differences elsewhere follow from rules we can state and test. Strict file matching is the right default for a benchmark that has to be repeatable; rules 3 and 4 are the two places where the maintainer may want a different choice.

## What this baseline says

1. The best single output so far is Claude run 4's findings record: all 30 planted flaws, with one flagged false positive. The run did not finish (no ledger, no report, stopped by context loss), so a user would not have seen a verdict.
2. Codex Pro moved from 24 to 25 found between kit 0.3.0 and 0.3.1, and from 5 to 2 missed, but 6 flaws changed status between the two runs. We cannot tell kit effect from run to run noise without repeats.
3. Every model output that carries a verdict says NOT READY, which is correct for this demo.
4. What the user saw varied far more than what the agents found. Claude run 1's agents found all 30 by hand count, while its reply shows 14 by this scorer.
5. The deterministic layer today, with no model, finds 8 of 30 (7 of 15 Free flaws). The earlier scorecard measured 3 of 30 with the older rules. The rules added since were written while looking at this demo, so the 8 is likely an overestimate of what they catch on an unseen app.

## What it does not say

It gives no detection rate for real products. It is one 46 file demo with obvious flaws, written by the same owner as the kit and the key. No output was produced three times under the same conditions, so stability is not measured. The Phase 0 exit criterion in `ENGINE-PLAN.md` (three runs of today's kit on the demo and two public vulnerable apps) is still open; it needs new model runs and, for the public apps, downloads, both of which wait for the maintainer.

## Proposed targets (for the maintainer to accept or change)

| Measure | Phase 1 (deterministic engine, 0.4.0) | Phase 3 (agent layer) |
|---|---|---|
| Stability | Byte identical findings, report and gate output over 3 runs of the same commit and tool versions | 100 percent on confirmed findings and verdict over 3 runs; leads may vary and the report says how many runs agreed |
| Recall on the demo, Free scope | At least the deterministic scan's 7 of 15, measured on a blind copy of the demo | At least 15 of 15 confirmed or partial, measured on a blind copy |
| Recall on the demo, all 30 | Report the number, no target (most Pro flaws need code map checks of Phase 2) | At least 25 found, the best finished model run so far (Codex Pro 0.3.1) |
| Flagged false positives | 0 | 0 on confirmed findings |
| Public apps | Measured on two approved targets from the list of candidate targets, no target set until the first measurement | Above the Phase 1 number on the same targets |
